# ADR 0002：订单与支付使用显式状态机

**状态**: Accepted
**日期**: 2026-10-09

## 背景

上游结账/支付接口存在大量「不确定终态」：命中 `unusual activity`、支付成功但订阅延迟生效、
3DS 未及时回调、上游 5xx 后交易状态未知。若用 `success: bool` 之类的布尔模型表达，
无法区分「请求成功」与「订阅最终生效」，会导致**重复扣款**或**过早交付**。

参考：`zkky` 已区分「请求成功 / 待确认 / 3DS next action / 订阅生效」；
`GPT-Register-Tool` 将 `account_deactivated` 归为永久失败。

## 决策

1. 订单与支付各有一套**显式枚举状态**，定义在 `packages/contracts/state.py`。
2. 状态迁移必须经过**合法迁移表**校验，非法迁移直接拒绝并告警。
3. 状态迁移事件必须落库，支持回放与断点续跑。
4. 只有 `active`（订阅已确认生效）才允许进入交付。

## 理由

- 幂等的前提是状态可判定：`unknown` 与 `failed` 的重试语义完全不同。
- 可观测：每次迁移都是审计点，便于定位「卡在哪一步」。
- 可恢复：进程重启后按状态表续跑，不重复扣款。

## 被否方案

| 方案 | 否决原因 |
|---|---|
| `success: bool` + `retry: bool` | 无法表达 3DS 与延迟生效，易重复扣款 |
| 只依赖上游返回码 | 上游返回码不稳定且信息不足 |
| 事件溯源 + 无当前状态 | 查询成本高，当前阶段过度设计 |

## 影响

- 所有服务必须经由 `packages/contracts/state.py` 迁移，禁止自由写状态字段。
- 新增状态需同步更新迁移表、`data-model.md` 与 `openapi.yaml` 枚举。
